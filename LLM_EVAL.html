CH 01

The Six-Layer Evaluation Framework

A modern LLM evaluation strategy is built on six interconnected layers. Each has a specific job, and if any is missing, the entire evaluation system fails in a predictable way. The NIST AI 800-2 draft structures the process into three stages — (1) defining the measurement target, (2) implementing and running the evaluation, and (3) analyzing and reporting results — and the six-layer model implements those stages concretely.

LayerPurposeFailure if Missing
DatasetInputs with expected behaviorScores nothing useful
MetricsRubric definitionsPass means whatever you want
JudgeScoring engineInconsistent rubric application
CI GateBlock bad PRsRegressions ship
Production ObservationScore live tracesDrift invisible until users complain
Closed LoopFailures back into datasetSame bugs ship twice

End-to-End Evaluation Flow

flowchart TD
    A[Define Evaluation Objectives] --> B[Select Benchmarks and Build Golden Dataset]
    B --> C[Design Evaluation Protocol]
    C --> D[Run Automated Benchmark]
    D --> E[Apply Metrics: Deterministic + Judge + Human]
    E --> F[Analyze Results and Calculate Uncertainty]
    F --> G{Meets Quality Gate?}
    G -->|Yes| H[Deploy / Promote to Production]
    G -->|No| I[Diagnose Failures and Iterate]
    I --> B
    H --> J[Monitor Production Traces]
    J --> K[Detect Drift / New Failure Patterns]
    K --> B
Key Takeaway The closed loop is what separates a living evaluation system from a static snapshot. Without it, evaluation is a one-time launch checklist.
CH 02

Evaluation Strategies in Depth

2.1 · Dataset Layer

Definition A versioned collection of inputs paired with expected behavior. For single-turn QA: (input, expected_output, retrieval_context?, metadata). For tool-using agents: (input, expected_tool_calls, expected_final_state, retrieval_context?, metadata).

Diagram — Dataset Construction Pipeline

flowchart LR
    A[Production Traces 100k raw] --> B{Privacy Scrub}
    B --> C[Clean Traces 60k]
    C --> D{Failure-Weighted Sampling}
    D --> E[Hard Cases 40 percent]
    D --> F[Edge Cases 35 percent]
    D --> G[Happy Path 25 percent]
    E --> H[Domain Expert Annotation]
    F --> H
    G --> H
    H --> I[Golden Dataset 50-100 per route]
    I --> J[(Versioned Dataset v1.2.0)]
    J --> K[CI Evaluation]
    J --> L[Judge Calibration]
    K -.new failures.-> D
    L -.disagreements.-> H

Real-Life Example — Enterprise Text-to-SQL Pipeline

A production text-to-SQL system filtered and reshaped privacy-scrubbed enterprise records from analyst workflows. Walk through the actual pipeline stages:

StageInputOutputYieldWhat Happened
Raw production traces100,000100,000100%Logged every analyst SQL query
Privacy scrubbing100,00060,00060%Removed PII-touching queries
Failure-weighted sampling60,00012,00020%Over-sampled rare query shapes
Expert validation12,0008,40070%7 in 10 approved
Final training set8,4008,400—Used to fine-tune Llama-3.3-Nemotron-Super-49B

Result. The fine-tuned model achieved 96% valid-query accuracy and a 2.50/5 semantic score, versus 94% and 2.35/5 for Claude Sonnet 4.5 on the same task.

Why the walkthrough matters. Notice the yields — only 8.4% of raw production traces became training data. The value was not volume but filtering. Failure-weighting at stage 3 is what moved the model above a frontier general-purpose model.

Key Takeaway Datasets must be sampled from production, weighted toward failures, and versioned like prompt releases. Start at 50–100 examples per route and grow weekly.
Common Pitfall Inventing examples instead of sampling from production. An invented dataset tests the author's imagination, not the model's real-world weaknesses.

2.2 · Metrics Layer

Definition The rubric definitions that map to failure modes you actually have. Three families: deterministic (exact match, schema validity, tool-call success), semantic (faithfulness, groundedness, context precision/recall), and conversation/outcome (task completion, dialogue reach to expected end state).

Diagram — Metric Selection Decision Tree

flowchart TD
    A[What is the task type?] --> B{Deterministic answer exists?}
    B -->|Yes| C[Exact Match / Schema Validation]
    B -->|No| D{Reference text available?}
    D -->|Yes| E{Surface form or meaning?}
    E -->|Surface| F[BLEU / ROUGE]
    E -->|Meaning| G[BERTScore / COMET]
    D -->|No| H{Multi-step agent?}
    H -->|No| I[LLM-as-Judge]
    H -->|Yes| J[Trajectory Eval + Judge]

The Metric Families Stack

┌─────────────────────────────────────────────────────────┐
│          CONVERSATION / OUTCOME METRICS                  │
│   Task completion · Dialogue reach · Multi-turn goal    │
├─────────────────────────────────────────────────────────┤
│              SEMANTIC METRICS (LLM-as-Judge)             │
│  Faithfulness · Groundedness · Context precision/recall │
│  Role adherence · Safety · Tone · Coherence             │
├─────────────────────────────────────────────────────────┤
│               DETERMINISTIC METRICS                      │
│  Exact match · Schema validity · Tool-call success      │
│  Citation validity · Length bounds · Format compliance  │
└─────────────────────────────────────────────────────────┘
     ↑ Higher cost, slower        ↑ Lower cost, faster
     ↑ Semantic nuance            ↑ Surface exactness

Real-Life Example — JUST-NLP 2025 Legal Translation

The JUST-NLP 2025 Shared Task for English-to-Hindi legal translation evaluated seven competing systems simultaneously.

RankSystemBLEUMETEORBERTScoreCOMET
1System A51.6175.8092.6176.36
4System D43.2070.1190.4471.20
7System G34.0865.2087.9365.20

Why the battery was necessary. BERTScore compresses to a narrow 87.93–92.61 range across all seven systems, while BLEU spans 34.08–51.61. A team choosing on BERTScore alone would see nearly indistinguishable systems; the BLEU and COMET spread reveals the real ranking.

Key Takeaway No single metric is sufficient. Use a battery of orthogonal metrics and always report uncertainty.
Common Pitfall Using a single aggregate score. A model can improve on one dimension while silently regressing on another.

2.3 · Judge Layer

Definition The scoring engine that applies metrics consistently. A calibrated judge requires four components: rubrics, ground truth, calibration, disagreement review.

Diagram — Four Building Blocks of a Calibrated Judge

flowchart TD
    A[1. RUBRIC: Plain-English criteria] --> B[2. GROUND TRUTH: Expert-scored traces]
    B --> C[3. CALIBRATION: Run judge vs expert]
    C --> D{Agreement 75 to 90 percent?}
    D -->|No| E[4. DISAGREEMENT REVIEW: Adjudicate, refine rubric]
    E --> A
    D -->|Yes| F[Production Judge DEPLOYED]
    F --> G[Weekly Recalibration]
    G --> C

Real-Life Example — State Farm Production Deployment

State Farm deployed LLM-as-a-Judge to monitor AI agents in production. Subject matter experts could only review less than 1% of total monthly messages, and thumbs-up/down feedback was sparse.

  1. Input to judge: (user_question, ai_answer, retrieved_context, rubric)
  2. Judge's job: Check every claim in the AI answer against the retrieved context.
  3. Autopay trace: Retrieved data had a payment_method and next_payment_date but no autopay field. The agent inferred autopay from the presence of a payment method — a classic hallucination a human reviewer at 1% sampling would never catch.
  4. Judge output: Score 1/5 with written reason.
  5. Value: The judge covered 100% of production interactions.

A second example, from PyCon Colombia: a team collected structured reviews from five domain experts across different insurance areas, then used DSPy to distill their judgments into a panel of calibrated LLM judges. A third example, HaluEval hallucination detection, achieved κ = 1.0 agreement with human annotation.

Key Takeaway LLM-as-a-Judge enables reference-free evaluation at scale, catching semantic failures that n-gram metrics miss.
Common Pitfall Deploying without calibration. Aim for 75–90% judge-to-human agreement before running against production data.

2.4 · CI Gate Layer

Definition Per-dimension thresholds asserted on every pull request that exit non-zero on the failing axis, not the aggregate.

Diagram — Per-Dimension CI Gate

flowchart TD
    A[Developer opens PR] --> B[Run eval suite on golden dataset]
    B --> C{Faithfulness >= 4.2?}
    C -->|No| X1[BLOCK: faithfulness regression]
    C -->|Yes| D{Safety >= 4.5?}
    D -->|No| X2[BLOCK: safety regression]
    D -->|Yes| E{Format compliance >= 95?}
    E -->|No| X3[BLOCK: format regression]
    E -->|Yes| F{Latency p95 <= 2000ms?}
    F -->|No| X4[BLOCK: latency regression]
    F -->|Yes| G[MERGE ALLOWED]
    X1 --> H[Comment on PR with failing dimension]
    X2 --> H
    X3 --> H
    X4 --> H
    H --> I[Attach eval artifact PNG]

Why Per-Dimension Blocking Matters

DimensionBeforeAfterΔGateVerdict
Faithfulness4.404.55+0.15≥ 4.2✅ Pass
Safety4.604.35−0.25≥ 4.5❌ FAIL
Format4.304.45+0.15≥ 4.0✅ Pass

The aggregate would rise (avg from 4.43 to 4.45) — a naive gate passes this PR. But the safety regression of −0.25 could ship a model that occasionally gives unsupported medical advice. The per-dimension gate blocks the merge.

Key Takeaway Gate on the metric that corresponds to your most expensive failure mode.
Common Pitfall Making evaluation "advisory" rather than blocking. Advisory gates are ignored under deadline pressure.

2.5 · Production Observation Layer

Definition Continuous scoring of live traces in production to detect drift, new failure patterns, and degradation.

Diagram — Production Observation Loop

flowchart LR
    A[User Request] --> B[Agent Pipeline]
    B --> C[Response to User]
    B --> D[Trace Logged async]
    D --> E[LLM Judge sampled 100 percent]
    E --> F{Scores below threshold?}
    F -->|Yes| G[Alert]
    F -->|No| H[Store Metric]
    G --> I[Triage Queue]
    I --> J[Human Review]
    J --> K{New failure pattern?}
    K -->|Yes| L[Promote to Golden Dataset]
    K -->|No| M[Tune Judge Rubric]
    H --> N[Weekly Drift Report]
    N --> O{Drift detected?}
    O -->|Yes| G

Real-Life Example — KDDI RAG Reliability Monitoring

KDDI deployed LLM-as-a-Judge to evaluate a RAG-based AI system across diverse content and use cases. The team traced a metric drop by examining individual production cases.

  1. Judge scored every production interaction on groundedness, summarization quality, and reasoning quality.
  2. A drop across multiple metrics appeared on one content type — not on all content, just one category.
  3. The team traced the cause by examining individual production cases from that category.
  4. Root cause was a distribution shift: user queries in that category had evolved to require information not present in the retrieval index.

Why offline eval would have missed this. The golden dataset from three months earlier contained no examples of the new query shape. Only live production scoring caught the drift.

Key Takeaway Production observability is distinct from offline eval. It catches distribution shifts that the golden dataset cannot predict.
Common Pitfall Treating offline eval as sufficient. A model that passes all offline tests can still fail on live traffic.

2.6 · Closed Loop Layer

Definition The feedback mechanism that promotes production failures into the golden dataset for the next iteration.

Diagram — The Closed-Loop Flywheel

flowchart TD
    A[Production Traffic] --> B[LLM Judge Scoring]
    B --> C[Error Feed: Failing traces]
    C --> D[Human Triage]
    D --> E{Dataset worthy?}
    E -->|Yes| F[Add to Golden Dataset]
    E -->|No| G[Log as known issue]
    F --> H[Retrain / Prompt Update]
    H --> I[CI Eval]
    I --> J{All gates pass?}
    J -->|Yes| K[Deploy to Production]
    J -->|No| L[Iterate on model / prompt]
    L --> I
    K --> A
    G -.monitor for frequency.-> D

Real-Life Example — NDD Long-Document VLM Pipeline

In a long-document vision-language model pipeline, evaluation failures determined which document types and reasoning modes were added next.

  1. Initial VLM evaluation on a fixed document set showed poor performance on multi-page grouped reasoning.
  2. The team expanded the dataset with four complementary generation streams: OCR-grounded text QA, classification-filtered visual QA, general single-page QA, and grouped-page QA.
  3. An independent VLM judge filtered examples for correctness, question quality, visual grounding, format compliance, and training-signal strength.
  4. Failures from each round determined the next round's document types and reasoning modes.

Why the closed loop matters. Without step 4, the team would have kept generating more of the same data. The loop turned evaluation failures into a data acquisition strategy.

Key Takeaway Without a closed loop, the same bug ships twice.
Common Pitfall Treating evaluation as a static snapshot rather than a continuously improving system.

Metrics in Depth

3.1 · BLEU (Bilingual Evaluation Understudy)

Definition N-gram precision between candidate and reference, with a brevity penalty. Final score = geometric mean of modified n-gram precisions (n=1..4) × brevity penalty BP = min(1, e^(1−r/c)).

Diagram — BLEU Computation

flowchart LR
    A[Candidate: 'the cat sat on mat'] --> C[Extract 1-4 grams]
    B[Reference: 'the cat sat on the mat'] --> C
    C --> D[Count matching n-grams]
    D --> E[Apply clipping: max = ref count]
    E --> F[Compute precisions p1 p2 p3 p4]
    F --> G[Geometric mean]
    G --> H[Apply brevity penalty]
    H --> I[BLEU Score]

Real-Life Example — Medical Brochure Translation

A statistical machine translation system for English-to-Sorani-Kurdish medicine brochures produced BLEU scores ranging from 22.65 to 48.93 across seven experiments. Post-processing with a medical dictionary improved one configuration to 56.87.

  1. Stage 1 (baseline): Raw SMT output scored 22.65 BLEU.
  2. Stage 2 (corpus expansion): Added parallel medical brochures → BLEU rose to ~35.
  3. Stage 3 (medical dictionary post-processing): Replaced mistranslated terms like "dosage" and "contraindication" with domain-correct alternatives → BLEU reached 56.87.
  4. Interpretation: A +21-point BLEU gain from dictionary post-processing alone.
Key Takeaway BLEU is suitable for translation and tasks with a well-defined reference.
Common Pitfall BLEU measures surface overlap, not semantic correctness. A semantically correct paraphrase scores lower than a semantically wrong copy.

Real-Life Example — Stock Price Headline Generation

A headline generation model was fine-tuned on 994 training examples from stock price fluctuation articles, using ROUGE as the evaluation metric.

  • Without fine-tuning: ROUGE-1 dropped to 2.56, ROUGE-2 to 0.29, ROUGE-L to 2.60.
  • With fine-tuning: ROUGE-1 reached 53.03, ROUGE-2 reached 35.73, ROUGE-L reached 52.77.
  • Manual validation: Of 100 test examples, 80 contained relevant information and 65 of those (81.3%) were appropriate as headlines. But 20 out of 100 contained incorrect information.
  • Interpretation: ROUGE measured recall of source content but was blind to the 20% hallucination rate.
Key Takeaway ROUGE is recall-oriented. It measures how much reference content is captured.
Common Pitfall ROUGE rewards copying source text, punishing natural paraphrasing, and cannot detect factual errors that happen to be lexically similar.

Key Takeaway BERTScore identifies semantic equivalence even when wording differs, accounting for synonyms and paraphrases.
Common Pitfall Computationally heavier than n-gram metrics and dependent on the quality of the underlying embeddings.

Definition The uncertainty of a language model when predicting text. Perplexity = exp(cross-entropy) = inverse geometric mean of the probability of the test corpus, normalized by word count.

  │                                              │
  │  Perplexity ≈ 8.7   (high uncertainty)       │
  └─────────────────────────────────────────────┘

Real-Life Example — Pre-Training Corpus Curation

  1. A reference small model is trained on a clean seed corpus.
  2. Every candidate document in the large unlabeled corpus is scored for perplexity under the reference model.
  3. Extremely low perplexity documents are often repetitive or boilerplate → remove.
  4. Extremely high perplexity documents are often gibberish, non-linguistic, or out-of-distribution → remove.
  5. The middle band (moderate perplexity) is retained for training.
Key Takeaway Perplexity is an intrinsic metric. It evaluates the model's internal probability distribution, not task performance.
Common Pitfall Perplexity does not measure reasoning, factuality, instruction following, or usefulness.

3.5 · Exact Match (EM)

Definition Binary score (1.0 or 0.0) based on exact string equivalence after normalization, usually with optional case-insensitivity and whitespace handling.

    D --> F["'paris'"]

    F --> G
    G -->|Yes| H[Score = 1.0]
    G -->|No| I[Score = 0.0]
    I --> J[SEMANTICALLY CORRECT but scored 0]
    H --> K[Semantically correct AND exact]

Real-Life Example — SQuAD Benchmark

  • Reference span: "the Eiffel Tower"
  • Model output "Eiffel Tower" → EM = 0 despite being correct.
  • Model output "the eiffel tower" → EM = 1 if case normalization is applied.

Why EM is still valuable. For structured outputs, code generation, and JSON-schema compliance, EM is the right metric because there is exactly one correct form.

Key Takeaway Exact Match is fully deterministic, zero-cost, and appropriate when there is exactly one correct answer.
Common Pitfall Brittle to phrasing. "The capital is Paris" versus "Paris" scores 0 despite being correct.

3.6 · LLM-as-a-Judge

Definition A judge LLM evaluates another model's output against a rubric written in plain English, returning a score and a written explanation.

Diagram — The Full Judge Pipeline

flowchart TD
    A[Test Case: input + context] --> B[Model Under Test]
    B --> C[Model Output]
    C --> D[Judge LLM]
    E[Rubric: plain-English criteria] --> D
    F[Ground Truth: expert score] --> D
    D --> G[Score + Explanation]
    G --> H{Agrees with ground truth?}
    H -->|Yes| I[Accept score]
    H -->|No| J[Disagreement Review]
    J --> K[Refine rubric]
    K --> E
    I --> L[Aggregate Metrics]

Real-Life Example — State Farm Production Deployment

  1. User question: "Am I enrolled in autopay?"
  2. Retrieved context: {"payment_method": "credit card", "next_payment_date": "01/15"} — no autopay field.
  3. Agent response: "Yes, you're enrolled in autopay."
  4. Judge input: (question, response, context, rubric).
  5. Judge output: Score 1/5 with reason: "Agent inferred autopay enrollment from presence of a payment method."
  6. Action: Trace logged, alert fired, ticket created, rubric refined.

Why this scale of monitoring matters. State Farm's subject matter experts could only review less than 1% of total monthly messages. The judge covered 100%.

Second example — PyCon Colombia insurance calibration. A team collected structured reviews from five domain experts across different insurance areas, then used DSPy to distill their judgments into a panel of calibrated LLM judges.

Third example — HaluEval. An LLM-as-a-Judge system achieved κ = 1.0 agreement with human annotation on HaluEval (20 examples, 100% factual error detection).

Key Takeaway LLM-as-a-Judge enables reference-free evaluation at scale, catching semantic failures that n-gram metrics miss.
Common Pitfall Deploying without calibration. Aim for 75–90% judge-to-human agreement before running against production data.

3.7 · Agent Trajectory Evaluation

Definition Trajectory evaluation assesses the entire sequence of messages — including tool calls, reasoning steps, and observations — not just the final output.

Real-Life Example — TRACE Framework

  1. TRACE introduces a reference-free framework for multi-dimensional evaluation of tool-augmented LLMs.
  2. It incorporates an evidence bank that accumulates knowledge from preceding steps, allowing it to assess reasoning trajectory.
  3. Validated on a meta-evaluation dataset with diverse flawed trajectories, each labeled with multi-faceted performance scores.
  4. Result: TRACE accurately evaluates complex trajectories even with small open-source LLMs.

TRAJECT-Bench. Constructs 5,670 "parallel/serial" tool-calling trajectories and "simple/hard" dual-difficulty queries using 1,228 executable real APIs. It refines evaluation from "whether the final answer is correct" to trajectory-level diagnostics focusing on "whether tools were selected correctly, parameters filled accurately, and sequence/dependencies met".

Key Takeaway A judge reading only the final response cannot see whether the agent called the right tool, looped unnecessarily, or failed to recover from a tool error.
Common Pitfall Output-only evaluation. Two agents reporting the same accuracy may not possess the same level of performance.

5.1 · Evaluation Harness (Pseudocode)

A three-tier scoring approach: rule-based checks (cheap, deterministic), LLM-as-a-Judge (semantic, scalable), and human review (ground truth).

import json
import random
from dataclasses import dataclass
from typing import List, Dict, Callable

@dataclass
class EvalCase:
    input: str
    expected_behavior: str
    context: str = None
    metadata: Dict = None

class LLMJudge:
    def __init__(self, model_fn: Callable, rubric: str):
        self.model_fn = model_fn   # e.g. call to GPT-5.4 nano or Claude Haiku
        self.rubric = rubric

    def score(self, case: EvalCase, output: str) -> Dict:
        prompt = f"""
        Rubric: {self.rubric}
        Input: {case.input}
        Context: {case.context}
        Output: {output}
        Return JSON: {{"reason": "...", "score": 1-5}}
        """
        response = self.model_fn(prompt)
        return json.loads(response)

class EvalSuite:
    def __init__(self, cases: List[EvalCase], judge: LLMJudge):
        self.cases = cases
        self.judge = judge
        self.results = []

    def run(self, model_fn: Callable) -> Dict:
        results = []
        for case in self.cases:
            output = model_fn(case.input, case.context)
            rule_score = self.rule_based_check(case, output)
            judge_score = self.judge.score(case, output)
            results.append({
                "input": case.input,
                "output": output,
                "rule_score": rule_score,
                "judge_score": judge_score,
                "metadata": case.metadata,
            })
        self.results = results
        return self.aggregate(results)

    def rule_based_check(self, case: EvalCase, output: str) -> Dict:
        checks = {}
        try:
            json.loads(output)
            checks["json_valid"] = True
        except Exception:
            checks["json_valid"] = False
        checks["within_length"] = len(output.split()) <= 500
        return checks

    def aggregate(self, results: List[Dict]) -> Dict:
        avg_judge = sum(r["judge_score"]["score"] for r in results) / len(results)
        pass_rate = sum(1 for r in results if r["judge_score"]["score"] >= 4) / len(results)
        return {
            "avg_judge_score": avg_judge,
            "pass_rate": pass_rate,
            "detailed_results": results,
        }

    def sample_for_human_review(self, n: int = 50) -> List[Dict]:
        return random.sample(self.results, min(n, len(self.results)))

# Usage
if __name__ == "__main__":
    cases = [EvalCase(input="What is the capital of France?",
                      expected_behavior="Paris")]
    rubric = """
    Score the response on faithfulness from 1 to 5:
    5 = every claim directly supported by retrieved docs
    1 = reply contradicts or invents facts
    """
    judge = LLMJudge(model_fn=my_llm_call, rubric=rubric)
    suite = EvalSuite(cases, judge)
    results = suite.run(model_fn=my_target_model)
    print(f"Average Judge Score: {results['avg_judge_score']:.2f}")
    print(f"Pass Rate: {results['pass_rate']:.2%}")

CH 07

Study Guide and Best Practices

Three Questions to Ask of Every Metric

  1. What failure mode does this catch? If it does not catch a failure you have, it is not worth the cost.
  2. What is the cost of false negatives vs. false positives? A CI gate that blocks a good release is costly; a production monitor that misses a hallucination is more costly.
  3. How will you calibrate and validate? Every metric, including automated ones, needs a ground-truth set and periodic recalibration.

The Ten Rules of a Production-Grade Eval System

  1. Calibrate your judge. Validate LLM-as-a-Judge against human labels weekly. If agreement drops below 75–90%, refine the rubric.
  2. Use statistical rigor. Calculate confidence intervals and p-values for metric deltas.
  3. Gate on the metric that corresponds to your most expensive failure mode.
  4. Avoid benchmark overfitting. Public benchmarks show concentrated top performance; use niche, task-specific benchmarks.
  5. Account for uncertainty. NIST recommends reporting error and uncertainty in results.
  6. Never show a score without its uncertainty. Error bars, confidence bands, or violin width.
  7. Draw the gate line. A dashed threshold turns an abstract number into a decision.
  8. Colour encodes identity, not rank. One colour per model, used consistently.
  9. Link everything. Click-to-filter is the single highest-value interaction.
  10. Ship static exports too. CI needs a PNG artifact attached to the PR.

The Three-Layer Minimum

If you only build three layers, build the dataset, the judge, and the CI gate. The other three — production observation, closed loop, and advanced visualizations — are how you keep the playbook honest over time.

Self-Assessment Questions

  • Can you draw the flow of your evaluation pipeline on a whiteboard in under two minutes?
  • For each metric you use, what is its ground-truth anchor, and when was it last calibrated?
  • If your judge's agreement with humans dropped by 10 points tomorrow, how would you detect it?
  • Which dimension would you most regret regressing on in production? Is that dimension gated?
  • What was the last production failure that became a test case in your golden dataset?
  • If you could only track one chart for the next quarter, which would it be, and why?
Closing Note A mature LLM evaluation system is not a score. It is a decision-making instrument: it tells you what to ship, what to block, and what to fix next. The six layers, seven metrics, and eight charts in this guide are the components; the discipline of the closed loop is what turns them into a system that improves every week.
